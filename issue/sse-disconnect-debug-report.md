# SSE Disconnect Debug Report

## Context

Issue observed in Mailman SSE flow:

1. Clicking `Disconnect` hides the button but stream continues receiving events.
2. `Loading...` overlay blocks response panel during long-lived streams.
3. After stream end, `Events` tab can appear empty while `Raw` tab still has content.

## Root Causes Identified

### 1) Disconnect not effective during live stream

- In `App`, the stream controller was originally stored only after `await sendRequestWithStreaming(...)` resolved.
- For endless SSE streams, that await does not resolve, so there is no active controller available while streaming.
- Result: `Disconnect` updates UI state but does not stop underlying stream read loop.

### 2) Loading overlay during stream

- `isLoading` was set `true` before request and only reset in `finally` after await completed.
- For ongoing SSE, await remains pending, so loading overlay persists and blocks response panel.

### 3) Events lost after stream completion

- Event callbacks correctly appended to `response.sseEvents` while streaming.
- On completion, app replaced response entry with final stream result object that did not carry `sseEvents`.
- Result: `Events` tab empty, while `Raw` stayed populated.

## What We Tried

### Attempt A: Lifecycle/state fixes

Implemented:

- Set loading false on `onOpen`.
- Preserve SSE event state by merging completion result instead of replacing response object.
- Pre-create and register disconnect controller before awaiting stream completion.

Outcome:

- Loading overlay behavior improved.
- Event persistence after completion improved.
- Disconnect still failed in runtime testing.

### Attempt B: Reader-cancel disconnect hardening

Implemented (then reverted):

- Extended stream controller to attach a reader cancel hook.
- On disconnect, called both abort and `reader.cancel()`.
- Added read-loop guard flag to ignore chunks after disconnect.
- Added regression test to verify `reader.cancel()` call.

Outcome:

- Unit tests passed.
- Manual runtime behavior still showed stream continuation after clicking disconnect.

## Current Status

- Disconnect remains unresolved in manual SSE scenario.
- Per request, latest disconnect-focused changes were reverted.
- Codebase remains with SSE support and other non-disconnect improvements.

## Suspected Remaining Gap

- The disconnect path may still not control the exact active reader/stream instance used by Bun fetch in real runtime.
- A runtime-specific behavior in Bun stream cancellation may require deeper control flow changes (e.g., explicit loop termination token tied to request ID, stronger ownership of active stream context, and event-ingest guard at App layer).

## Recommended Next Investigation

1. Add runtime instrumentation logs for one stream session:
   - disconnect clicked
   - abort signal fired
   - reader cancel called
   - read loop iteration after abort
   - onEvent callback after disconnect
2. Confirm whether events are still generated by active read loop or by stale callback closures.
3. Move to single authoritative per-request stream session token and reject stale events in App reducer.
